# 手绘动画实战笔记

**从一个彩色插画，到一段"有人在画"的逐笔手绘视频。**

这篇文档以「旗袍豌豆射手」为参考案例，把整条流水线、我在上面踩过的坑、以及怎么把质感做上去，都摊开写清楚。坑的部分我不打算美化——里面大多数错误都是我自己犯的，而且有几个是"看起来完全正常、数据还很漂亮"的那种，值得单独记下来。

---

## 0. 这篇文档适合谁看

想用 Manim 做这类效果的人。前提是已经装了 Manim，并且了解 `Create` / `VMobject` 这些基础。

配套代码三个文件：

| 文件 | 作用 |
|---|---|
| `extract_assets.py` | **彩图 → 素材**：分割人物、炼线稿、分层色块、几何标定 |
| `pea2_scene.py` | **素材 → 视频**：逐笔手绘、几何构造、分色上色、结尾动效 |
| `手绘动画实战笔记.md` | 就是本文。**第 4 节是给 AI 看的操作规程，最该被复用** |

`extract_assets.py` 对任意彩图都能跑，不限于这个案例。

---

## 1. 全流程总览

分成「离线派生素材」和「在线渲染动画」两段。素材派生慢、可反复调参；渲染慢、应该建立在已确认的素材上。

```
                     彩色插画 (source.png)
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   [1] 分割人物          [2] 炼线稿            [3] 分层色块
   到背景色的距离        mkbitmap 高通滤波      HSV 按色相切
   形态学清理            蒙版滤背景杂点         白/绿/红/蓝/粉
   最大连通域            去小碎点
        │                     │                     │
        ▼                     ▼                     ▼
   full.png              lineart.png           lay_*.png
   (去背景角色)          (alpha=墨迹)          (各层透明色块)
                              │                     │
                              ▼                     │
                    manim-handdraw 抽取             │
                    骨架化→交叉点断开→游走          │
                    →合并(顺带补缺口)→排序          │
                              │                     │
                              ▼                     │
                        326 段笔画路径              │
                              │                     │
                              └──────────┬──────────┘
                                         ▼
                               [4] 逐笔手绘 + 几何构造
                                   + 分色扫入上色
                                         │
                                         ▼
                                   1080p60 成片
```

**关键认知：这张彩图和上一张牛仔豌豆一样难，不是特例。** 区别只是那张的背景是透明的、这张是有纹理的。整条流水线是通用的。

## 2. 我踩过的坑

按性质分四类。每一条都写了「现象 → 我以为是 → 实际是 → 怎么改 → 教训」。

### 2.1 方法与流程

#### 坑 1：忘了自己做过

**现象**：拿到新图，我把它当成一个全新的难题去设计流水线，还准备跟用户解释"这张是彩绘所以更麻烦"。

**实际是**：上一张同样是彩图，我早就用 `去背景 → 色彩量化 → 按色相分层 → mkbitmap 提炼线稿 → potrace 矢量化` 走通过一遍。工作目录里还留着当时的中间产物（`pea_flat_colors_opt.png`、`color_layer_green_opt.png`、`pea_lineart.bmp`）。

**怎么改**：用户提醒后我翻了旧目录，从留下的中间文件把整条流水线反推了出来，工作量比重新设计小一个数量级。

**教训**：
> 动手前先翻上次的产物。**中间文件是无声的文档**——它们记录了每一步长什么样，比回忆可靠。而且这次已经是第二次吃亏了：上一轮我把骨架遍历脚本弄丢过一次，只能重写。

这也是为什么这次我坚持把提取逻辑落成 `extract_assets.py` 一个独立文件，而不是散在几个一次性脚本里。

---

#### 坑 2：把"实心区域"当普通线条处理

**现象**：mkbitmap 给出的线稿里，眼睛和炮口开口是一圈**轮廓**，中间是空的。骨架化之后，一个实心眼睛被画成**一条穿过中间的细线**——完全不像原画。

**实际是**：mkbitmap 是"边缘/线条"提取器，对实心色块它只能描边。而骨架化处理的本来就是线，实心块进去出来必然退化成中线。

**怎么改**：把实心块识别出来（`luma < 95 & sat < 60` 再形态学开运算），从逐笔绘制里**剔除**，改用几何构造绘制：参数方程画椭圆 → 墨线沿椭圆描一圈 → 墨团从中心涨开填实 → 点高光留白。

**教训**：
> 线稿提取器和实心色块是两类东西。**必须先分类，再分别用合适的方法画**。指望一个工具同时处理两者，结果就是眼睛变成一条线。

---

#### 坑 3：差点把头发"清理"掉

**现象**：分割出人物后，头发外围有一圈灰蒙蒙的晕。我觉得"放在米色画纸上会显脏"，写了规则把它去掉。

**验证时发现**：去掉之后头发**破成一块一块的**，白色缝隙到处漏，比留着难看得多。

**实际是**：那圈灰晕是**蓬松头发的体积感**本身——原画里发丝向外逐渐变淡、消失在背景里，那个渐变就是头发的边缘。

**怎么改**：原样保留。合成到画纸色上看了一眼，灰晕读起来就是柔软的发丝，不脏。

**教训**：
> **先看，再删。** 我差点凭"感觉会脏"就删掉了一个真实的画面特征。任何"清理"操作，都要先合一张图看效果，再决定。

---

#### 坑 4：上色层互相覆盖而不是累积

**现象**：上色阶段，红领巾上完色就消失了，蓝衣服上完也消失了。用户直接指出来了。

**实际是**：我在上色循环里写了一句 `FadeOut(holder)`——每上一层新颜色就把**上一层淡出**。而上一版（牛仔）是**累积**的：绿、棕、红都留着，最后才被完整图一起取代。是我这次自己写岔了。

**怎么改**：去掉那行，让五层分色逐层叠加、互相保留，最后完整图扫上来时再统一收掉已被完全覆盖的分色层。

```
银发落下 → 绿头压上来（银发还在）→ 红巾上色（前两层都在）
→ 蓝衫铺开（红巾还在）→ 桃花点染（全都在）
→ 完整图扫入收束明暗
```

**教训**：
> 参考上一版能跑的实现时，**别凭印象重写**。同一个效果，"累积"和"替换"差别巨大，而我当时以为两者等价。

---

#### 坑 5：改一个参数就重渲 4 分钟

**现象**：早期每次改完就整片渲染，一二十分钟才看到结果，而且经常在很后面才报错。

**怎么改**：
- 用 `manim -n 起始,结束` **只渲染一个片段**（比如只跑上色那 20 个动画，40 秒出结果）
- 参数扫描先出**接触印相表**（一张图里并排 9 组参数），肉眼挑
- 素材阶段完全不碰 Manim——先用 PIL 出对照图确认，再进渲染

**教训**：
> 渲染是最后一步，不是验证手段。**能用静态图验证的，就不要用视频验证。**

---

#### 坑 21：把动画截图当成角色插画

**现象**：拿到一张动画截图（角色站在云层背景前，顶部还有字幕和 TR 水印），直接跑脚本。结果：人物蒙版占了**整张图的 95.6%**，等于没去背景；分层里白层 41%、蓝层 29% 全是背景云；几何标定检出 12 个"暗块"，椭圆圈在了手臂和背景云上。

**实际是**：脚本的核心前提是「**背景大致是单一颜色、且和角色有明显色差**」。前两张图（透明背景 / 米灰背景）成立，这张不成立——背景本身横跨明暗蓝白（云），角色的白发又和背景亮部撞色。后三步全是被第一步连累的。

**怎么判断**：跑之前先看**四边中位色到全图的距离分布**。正常情况中位数应该不大（背景占多数像素）；这张的中位数是 **162**（90% 处 214），说明"背景色"根本不是多数像素的颜色——前提在开跑前就已经破了。

**教训**：
> 脚本有前提，前提要用**数值**验，不能凭"看起来是个角色图"就往下跑。
> 另外：**水印和字幕会被当成线稿画进去**，而且面积大，碎点过滤删不掉——这两样必须提前挡掉。

---

#### 坑 22：透明 PNG 的透明区填什么颜色，会决定结果好坏

**现象**：既然透明背景最理想，我造了两张透明背景的图来测——透明区分别填白和填黑。结果：**填白那张漏掉 57512 像素**（正是角色的白发），与真实蒙版 IoU 只有 94.2%；填黑那张 IoU 100%。同一张图，只因为**不可见像素**里存的值不同，结果就不一样。

**实际是**：脚本读图时直接 `.convert("RGB")`，**完全没有用 alpha 通道**，于是退回按背景色分割。透明像素里存的 RGB 是导出工具随手填的（有的填白、有的填黑），脚本照着它算颜色距离就被带偏了——填白时，"白色背景"和角色的白发没有色差，白发被当成背景漏掉。

还有第二层：即使改用 alpha 通道，透明区仍要填个中性色再交给 `mkbitmap`，否则轮廓处的强色阶会让高通滤波**振铃**。实测墨量：填黑 **+49%**、填白 +12%、填灰 +23%、**填「轮廓内一圈的中位色」+1%**。

**怎么改**：
1. **优先用 alpha 通道当蒙版**——这是最可靠的"角色在哪"信号，比任何颜色分割都准
2. 透明区填成**轮廓内一圈像素的中位色**（这个颜色能从图本身算出来，不需要知道原始背景）

改完三种输入（原图 / 透明填白 / 透明填黑）产出**完全一致**，五层色块一个像素都不差。

**教训**：
> 「透明背景最好」这句本身没错，但**前提是你真的读 alpha**。
> 一个被忽略的通道，能让"最好的输入"变成"比原来还差的输入"。
> 而且——**结果不应该取决于不可见像素里存了什么**。这个 bug 很隐蔽：换个导出工具，同一张图就跑出不同结果。

### 2.2 几何标定

#### 坑 6：拟合出一个"数据很漂亮"的荒谬圆

**现象**：我要拟合炮口外缘，做法是"逐行取最右侧的人物像素，然后拟合圆"。结果出来：中心 `(1.566, 0.239)`、**半径 1.564**（整个角色才 6 个单位高），而且报告"内点 529/602"——看着还挺可信。

**实际是**：我的扫描带写成了 `y ∈ [0.22H, 0.70H]`，这个范围**跨到了头发区域**。在那些行上，最右侧像素是头发的边缘而不是炮口，于是拟合出的是一个包住半个身子的大圆。

**怎么发现的**：两个警报——
1. 半径大得不合常识；
2. **弧段角度范围 0°~359.8°**。真正的一段圆弧不可能覆盖整周。这是拟合跑飞的典型信号。

**怎么改**：扫描带改成从**已检出的特征**推导——先用开口的位置和尺寸算出炮口的纵向范围，再去扫。

**教训**：
> 两件事。第一，**扫描范围不能拍脑袋给**，要从已知特征推。第二，拟合完必须看两个体检指标：**残差**和**弧段角度跨度**。只报"内点比例高"是会骗人的——一个包住半个身子的圆，对它自己那批点确实拟合得很好。

---

#### 坑 7：用"有没有被包住的洞"来认眼睛

**现象**：我想自动识别哪几个暗块是眼睛。思路是"眼睛里有高光，高光就是被暗块包住的洞"。结果**一个都没检出**。

**实际是**：原画里眼珠的高光**贴着瞳孔边缘**（不是悬在中间的圆点）。在"非暗块"的连通域里，这个高光和整片背景连成了同一个巨大连通域，质心在画面中央，自然被"质心要在椭圆内"的判据全部过滤掉。

**怎么改**：换判据——**在椭圆内部找最亮的区域**，而不是找"被包住的洞"。

**教训**：
> "洞"这种依赖拓扑的判据很脆。**只要目标有一处贴边，拓扑就变了。** 改用"在给定区域内找极值"这类几何判据，鲁棒得多。

---

#### 坑 8：用外接矩形近似倾斜椭圆

**现象**：早期我用暗块的**外接矩形**当椭圆参数（宽/2 当短半轴、高/2 当长半轴、再加一个倾角）。

**实际是**：对倾斜椭圆，外接矩形会**同时把长短轴算大**，倾角也有偏差。第一版眼睛参数 `A=0.171 B=0.291 倾角=6.4°`，二阶矩给的是 `A=0.286 B=0.157 倾角=-83.5°`——描述的是同一个椭圆，但参数差很多，直接影响圆规和描线的落点。

**怎么改**：用**二阶矩**拟合。对均匀填充的椭圆，二阶矩给出的长短轴是**无偏**的。

**教训**：
> 数学工具挑准确的那个。外接框是"像素统计"，二阶矩才是"形状拟合"。

---

#### 坑 9：把参数硬编码成"我肉眼量的"

**现象**：第一版扫描炮口轮廓写的是 `for py in range(370, 566)`——就是我看图估的像素范围。

**实际是**：换一次裁切、换一次导出尺寸就废了，而且这个魔法数字完全没有解释力。

**怎么改**：改成从已检出的开口位置和尺寸推导扫描带：
```python
cav_a_px = cavity[2] / SIZE * H
row0 = int(cav_py - 1.75 * cav_a_px)
row1 = int(cav_py + 1.75 * cav_a_px)
```

**教训**：
> 魔法数字是欠债。**凡是能量出来的，就不要写死。**

### 2.3 Manim / 代码层面的坑

#### 坑 10：`VGroup` 装不了 `ImageMobject`

```python
VGroup(img1, img2)   # TypeError: Only values of type VMobject can be added
```
`VGroup` 只收 `VMobject`；`ImageMobject` 得用 `Group`。**报错信息完全不提示这一点。**

我为此浪费了一次 4 分钟的完整渲染（错误发生在很后面的上色阶段）。

#### 坑 11：`VMobject` 子类的属性不能叫 `points`

我把墨团的顶点数存成 `self.points`，撞上了 Manim 自己存**原始点数组**的同名 property。赋值被 setter 转成 0 维数组，而报错要到很久之后才从 `np.linspace` 里冒出来：

```
TypeError: only integer scalar arrays can be converted to a scalar index
```
完全看不出源头。改名 `n_points` 解决。

#### 坑 12：`move_to` 要三维点

笔画数组天然是 `(n, 2)`，`move_to` 需要 `(3,)`。要么补 z 分量，要么在库层面统一补。

#### 坑 13：场景方法当模块函数调

`construct_ellipse` 是 `HandDrawScene` 的**方法**，不是模块级函数。我写成 `hd.construct_ellipse(self, ...)` 直接 `AttributeError`。

#### 坑 14：两个同名的 `label` 返回类型不同

```python
from scipy.ndimage import label     # 返回 (labeled, num)
from skimage.measure import label   # 返回 labeled
```
同一个文件里两处都用了，一处写 `lb = label(x)`，另一处写 `lb, n = label(x)`，必然有一处炸。

#### 坑 15：色相区间和 `zip` 配对

跨 0 度的红色，我写成 `[[0,25],[335,360]]`，然后用 `zip(hlo, hhi)` 配对 → 变成 `(0,335)` 和 `(25,360)`——**第一段就覆盖了大半个色相环**。红层面积从 5.9% 暴涨到 **49.6%**。

**是怎么发现的**：我在脚本里加了**像素数统计**，一眼看出 49.6% 不合理（红色的领巾不可能占半个角色）。

**教训**：
> 跨 0 度的区间要显式写成两段分别取或。而且——**给每一步加数值输出，让 bug 自己喊出来。** 如果只看最终视频，这个错误表现为"红领巾糊了一大片"，很难定位到是 `zip` 的问题。

#### 坑 16：`UpdateFromAlphaFunc` 内部已经套过 `rate_func`

再套一次相当于把缓动函数用了两遍，节奏会不对。

### 2.4 产品化之后的坑（跨平台）

这三条是做完整合发布时才暴露的，但值得一起记着。

#### 坑 17：`open()` 不写编码

```python
open(path, "w")          # 用系统 locale 编码
```
- 西文 Windows（cp1252）：写中文直接 `UnicodeEncodeError`
- **中文 Windows（cp936）：静默写成 GBK**——而 Python 拒绝把 GBK 当源码解析，报的是语法错误，**你根本想不到是编码问题**

所有文件读写都显式 `encoding="utf-8"`。

#### 坑 18：字体只有 mac 上有

`PingFang SC` / `Menlo` 在 Windows / Linux 上不存在。而 **Manim 对缺失字体是静默替换**——我实测过：不抛异常、连 `warnings` 都不发一条。所以非 mac 用户会**在毫无提示的情况下**换一套字形；如果那台机器连中文字体都没装（精简 Linux 镜像），中文会变成一排方框。

改成走跨平台候选链（微软雅黑 / Noto Sans CJK SC / 思源黑体 / 文泉驿正黑）。

#### 坑 19：上色接管后没淡出墨线

成品图铺上来之后，如果墨线层还留在场景里，角色一旦位移（后坐力）动的是颜色图、底下的线稿不动，边缘就会**漏出一层幽灵轮廓**。

#### 坑 20：切片取整产生接缝

把成品图切成 7 条竖条扫入。每条按"算出自己的宽度、再乘 7"推位置，会因为取整在相邻条之间留下约 1 像素错位，在角色身上表现为**一条竖直的细缝**。

正确做法：边界用 `round(i*W/n)` 算，每条按自己**精确的** `[x0, x1]` 摆放。

## 3. 怎么追求质感

坑是"不出错"，质感是"好看"。这部分是我觉得真正拉开差距的地方。

### 3.1 每一步都出对照图，不靠猜

这条是贯穿全程的方法。举几个具体做法：

| 环节 | 对照方式 |
|---|---|
| mkbitmap 参数 | 3 滤波半径 × 3 阈值 = **9 宫格接触印相表**，一眼挑出最好那组 |
| 分割阈值 | 4 个阈值四宫格，看头发保不保得住 |
| 几何标定 | 拟合出的椭圆**叠回原图**，用洋红圈画出来看严不严 |
| 线稿质量 | 清理后的笔画**并排贴在原线稿边上**，比覆盖率更直观的是"看起来像不像" |
| 上色分层 | 五层单独铺在画纸色上看，确认每层抓的颜色对 |
| 清理操作 | 去掉灰晕**前后合成对比**，一眼看出去掉更糟 |

**收益**：上面 2.1 的坑 3（灰晕）、2.2 的坑 7（高光漏检），都是在对照图上当场发现的，没有流到成片里。

### 3.2 数值回归

改完一个规则，**对比改前改后的像素数**。

坑 15 那个 `zip` 配对错误，红层从 5.9% 变成 49.6%——如果脚本不打印像素数，这个 bug 会伪装成"红领巾糊了一大片"这种视觉问题，排查方向完全不同。

我现在写这类脚本，每一步都会 `print` 一个可验证的数字：墨迹像素数、各层占比、笔画数、总长、预计时长。

### 3.3 节奏感来自"像人"，而不是"像机器"

逐笔手绘好看的关键不是线条本身，是**运笔的节奏**：

- **时长按笔画长度分配**，而不是每笔固定时长。长线画得久、短线收得快，接近真人。
- **笔尖光标实时跟住笔迹推进的前端**（沿曲线走，不是直线滑到终点）。
- **逐笔顺序按人的习惯排**：先按行分带（从上往下），带内再贪心就近接着画。纯按 y 排序会左右横跳，纯最近邻会从角落开始。
- **笔画之间的搭接**：交叉点处把相邻笔画的端点沿各自切线方向外延一点，缺口自然接上，而且聚在一起的小碎段会**连成一条线**而不是被当成噪点删掉。

### 3.4 线条粗细的两种思路

这个案例最终用的是**等宽细线**（`stroke_width=3.0`，1080p 下约 3.6px），因为用户要的是"第一版那种细线"。

但中间做过一版**笔锋变宽**的，技术上值得记一笔：

- 从原线稿做**距离变换**，得到每个骨架点上的局部墨半宽 → 恢复出原画每条线的真实粗细
- 沿中心线生成**变宽带状多边形**（中段饱满、起收笔尖细）
- 叠一层半透明**洇墨光晕**（宽度用"笔宽 + 固定偏移"而不是简单乘倍数，这样细线细边、粗线粗边，符合洇墨的物理直觉）
- 随机**飞白**收细、起笔**甩墨点**

效果上确实更有毛笔味，但代价是线条变粗、观感变重。**这不是技术取舍，是风格取舍**——同一套代码可以出两种味道，取决于要什么。

### 3.5 诚实边界 —— 以及谁来补上这段

有件事我没有假装能做到：**工具不认识画面内容**。

它只看到"墨"和"背景"。哪几笔构成眼睛、炮口圆心在哪、圆规该描哪个圆——这些必须**测量 + 核验**。

关键问题是：**谁来做核验？** 我的第一版答案是"人工确认"，这是错的。正确的答案是：

> **由具备视觉能力的 AI 来做。核验不需要人类。**

这件事之所以成立，是因为 AI 能读诊断图，而错误在图上是一眼可见的（那个拟合出半径 1.564 的圆，数字报"内点 529/602"看着很可信，画回原图上却包住了半个身子）。所以 `extract_assets.py` 的做法是：

- 提供测量工具（二阶矩椭圆拟合、稳健圆拟合、暗块检测）
- **把结果叠回原图**，输出一张"为被看而设计"的诊断图
- 由 AI 读这张图判断对错，**改判据而不是改数字**，再重跑
- 自检不通过就**醒目报警**，绝不静默交出错的几何参数

这套循环的完整写法和可照做的清单在 **第 4 节**，那是本文档里最该被复用的一节。

## 4. 让有视觉的 AI 审核输出（可复用工作流）

这一节是给 AI 看的操作规程。

### 4.1 为什么必须有这一步

几何标定**不可能只靠数值判断对错**。看这个真实例子：

我拟合炮口外缘，得到中心 `(1.566, 0.239)`、**半径 1.564**——而整个角色才 6 个单位高。程序输出的体检数据是「**内点 529/602**」，看着非常可信。

原因是我逐行取最右像素时，扫描范围跨到了头发区域。**数字骗人，图不骗人**：把那个圆画回原图上，一眼就能看出它包住了半个身子。

同一类错误还有一次：脚本报「眼睛 2 个」，但那是背景里两个暗云块——数字对，内容错。

所以流程必须是：

```
脚本给出候选  →  脚本把候选叠回原图  →  AI 读图  →  判断对错
      ↑                                                    │
      └──────────  改判据（不是改数字）  ←─────────────────┘
```

### 4.2 诊断图要怎么出（三条硬要求）

1. **叠回原图**，不要单独出一张白底的候选图。只有在原画上才能看出"圈住的到底是不是那个东西"。
2. **用高对比色**，洋红 / 橙 / 青这类原画里不会出现的颜色。别用红色——原画本身可能就有红。
3. **给候选编号，并把编号印在图上。** 这样 AI 才能说"第 3 和第 5 个是误检"，而不是"左边那个"。

同时打印一张候选表，让 AI 能把图和表对照着看：

```
    面积      中心px          平均饱和度   判断
   21367   (1065,  643)        49.8      眼睛/开口（近中性暗）
   15986   ( 679,  862)        95.7    ★ 误检（高饱和=暗红）
   12393   ( 393,  752)        90.1    ★ 误检（高饱和=暗红）
    7914   ( 733,  471)         4.5      眼睛/开口（近中性暗）
```

`extract_assets.py` 会自动输出这两样：`diag_geo.png`（叠加图）+ 终端里的候选表。

### 4.3 判断什么 —— 核对清单

AI 读诊断图时逐条过：

| 检查 | 不合格的表现 |
|---|---|
| 每个椭圆是否**紧贴**目标轮廓？ | 偏大 / 偏小 / 偏心 / 倾角不对 |
| 有没有**误检**（圈在了不该圈的地方）？ | 圈在衣服、阴影、手臂、背景上 |
| 有没有**漏检**（该圈的地方没圈）？ | 两只眼睛只圈出一个 |
| 眼睛候选**是否恰好 2 个**？ | 3 个以上 → 判据太松 |
| 两个眼睛**尺寸是否接近**？ | 一个比另一个大 3 倍 → 其中一个是误检 |
| 两个眼睛**是否大致对称**分布在中线两侧？ | 都挤在一边 → 判据有问题 |
| 候选是否都落在**人物蒙版内部**？ | 跑到背景上 → 上游分割已经崩了 |
| 拟合的**弧段角度跨度**是否合理？ | 跨满 360° → 拟合跑飞了 |

最后两条程序也能自检，见 4.5。

**如果多条不合格、尤其是"候选落在蒙版外"，别继续调判据** —— 那说明上游的分割（去背景）已经失败，判据再准也是在错的候选里挑。此时应回头修分割。

### 4.4 改什么 —— 改判据，不要改数字

发现误检后，**千万不要**把某个块的坐标硬编码排除掉。那对这张图有效，换一张就废。

要找的是**能把两类分开的一般性特征**。真实案例：

第一版判据是 `luma < 95`，检出 7 个块、其中 3 个误检。我把它们的平均饱和度算出来一对：

| 实际是什么 | 平均饱和度 |
|---|---|
| 眼睛 / 炮口开口（真目标） | 4.5 ~ 49.8 |
| 领巾 / 领口（误检，暗红） | 90.1 ~ 137.4 |

**中间有一道干净的间隔。** 于是判据加上 `& (sat < 60)`——一行，而且能泛化：任何暗红色块都会被排除，不管它在这张图的哪个位置。

这一步的产出不是"这张图的正确答案"，而是**一条一般性规则**。

### 4.5 让脚本自己发现"猜错了"

AI 读图能抓到错误，但每次都靠读图不理想。**把常识写进自检**，不满足就报警——`提取图像脚本.py` 里已经实现（函数 `sanity_check()`），共 7 条：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 暗色实心块总数 ≤ 6 | 正常角色一般 1~4 个（眼睛 + 开口 + 少量细节）。数量爆炸基本只有一个原因：**上游分割没去干净背景**，背景的暗部被算了进来 |
| 2 | 眼睛候选恰好 2 个 | 0 个 = 没找到；1 个 = 漏检；≥3 个 = 判据太松 |
| 3 | 两眼长半轴相差 ≤ 2.5 倍 | 差太多说明其中一个不是眼睛 |
| 4 | 两眼大致在同一水平带上 | 允许侧脸倾斜，但纵差超过 1.2 倍眼长就不像同一张脸 |
| 5 | 眼睛中心落在人物蒙版内 | 落在外面 = 上游已经错了 |
| 6 | 能找到开口候选，且不比眼睛小 | 开口通常比眼睛大 |
| 7 | **人物蒙版占全图比例 ≤ 85%** | ——这条是**最有效的单条判据**，见下 |

第 7 条值得单独说：它是"**上游分割失败**"最直接的信号。角色插画的蒙版通常占 5%~80%；一旦接近整张图，说明背景压根没被分开，那后面所有步骤都是在一堆错的候选里挑——判据再准也没用。

实测：一张角色插画 63%（通过）；一张动画截图（云层背景）跑到 **95.6%**，于是把背景的暗云当成眼睛、把云的颜色当成角色图层。加上这一条之后，那张图**不需要任何人工介入就会自己报警**：

```
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
自检未通过 —— 几何标定结果很可能不可用，请勿直接用于渲染：
  1) 检出 12 个暗色实心块（正常角色一般 1~4 个）。很可能是上游分割没去干净
     背景，背景的暗部被算了进来。
  2) 人物蒙版占了整张图的 95.6%，背景基本没被分开。图层与几何标定都不可信
     —— 请换一张背景更干净的图（单色背景或透明背景），或先单独做抠图。
  → 打开 diag_geo.png 核对。若确认标错，先解决上游的分割问题
    （背景没去干净是最常见原因），或换一张背景更干净的图。
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
```

同时把结论写进 `geo.json` 的 `sanity` 字段，让下游程序也能判断：

```json
"sanity": { "passed": false, "problems": ["…"] }
```

**这样"错得离谱"的图会自己喊出来，而不是静默交出一份错的参数。**

#### 一个真实的协作事故：重复定义把自检架空了

这道自检不是我一个人写的。第一版由另一个 AI 加进来（6 条判据），后来我凭印象往同一个文件里又插了一份自己的 `sanity_check()`——**结果我的那份定义在后面，把前面的整个覆盖掉了**（Python 里同名函数后定义者生效）。我的弱版没有"暗块总数"这条，于是那张动画截图的 12 个暗块照样判成"通过"。

我是靠 `grep -n "def sanity_check"` 数出有 **2 个定义**才发现的。

**教训**：
> **改多人协作的文件之前，先看一眼它现在长什么样。** 我当时的心理是"这是我自己写的文件"，但它已经被别人改过了。
> 具体手法：`grep -c "def 函数名"` 数定义数；改完再数一遍。**同名函数被静默覆盖，不报错、不警告，只是行为悄悄变了。**
> 修完之后要**双向验证**：好的输入仍然通过（回归），坏的输入确实报警（新能力）。只测一边等于没测。

### 4.6 完整循环（照着做）

```
1. 跑脚本，拿到 diag_geo.png + 候选表
2. 读 diag_geo.png，按 4.3 的清单逐条过
3. 有不合格
     ├─ 候选落在蒙版外 / 大面积不合格 → 回头修上游分割，别调判据
     └─ 只是误检或漏检     → 到候选表里找可分的特征，在 4.4 的意义上改判据
4. 重跑，回到第 2 步
5. 全部合格 → 看自检有没有报警（4.5）
6. 通过 → 这批几何参数可以用了
```

循环通常 2~3 轮。本案例是：第一版 7 个块（3 个误检）→ 加 `sat<60` → 3 个块全对。

### 4.7 一句话总结

> **工具负责测量，AI 负责看图核验，判据负责泛化。**
> 三者缺一不可：只有测量会自信地给你半径 1.564 的圆；只有看图则每张图都要重来；只有判据则不知道判据对不对。

### 每次都要做的三件核验

1. **`diag_pipeline.png`** —— 分割有没有把人物切残？线稿杂点多不多？分层抓的颜色对不对？
2. **`diag_geo.png`** —— 椭圆圈在眼睛和开口上了吗？有没有误检的暗块？（对照第 4 节的核对清单）
3. **成片抽帧** —— 渲染完在**关键时间点**抽帧看（不只是看时长和文件大小）。重点看：逐笔阶段、构造特写、上色过程、结尾。

三件都由 AI 读图完成，**不需要人类**。第 1、2 件在派生素材后立刻做，别等到渲染完才发现几何标错了。

## 7. 一页速查：容易忘的

- 动手前**先翻上次的产物和中间文件**
- **先看，再删**（任何"清理"操作都要先合成对比）
- **给每一步加数值输出**，让 bug 自己喊出来
- 拟合完看**残差 + 弧段角度跨度**，别只看内点比例
- **几何标定必须让有视觉的 AI 读叠加图核验**（第 4 节），核验是 AI 的活、不需要人类
- 误检了要**改判据而不是改数字**（找可分的特征，如 `sat<60`，不是硬编码排除某个块）
- 改多人协作的文件前**先数一遍同名函数定义数**（`grep -c "def f"`）—— 重复定义会静默覆盖
- 修完自检要**双向测**：好输入仍通过 + 坏输入确实报警
- **扫描范围从已知特征推导**，不写魔法数字
- 倾斜椭圆用**二阶矩**，不用外接框
- "有没有洞"这种拓扑判据很脆，优先用区域内的几何极值
- **形似的东西别凭印象重写**（累积 vs 替换）
- **能用静态图验证的，不要用视频验证**；必须渲染时用 `-n` 只跑片段
- `VGroup` 不装 `ImageMobject`；`points` 是保留名；`move_to` 要三维
- `open()` 永远写 `encoding="utf-8"`
- 字体要跨平台候选链，因为 Manim **静默替换**缺失字体
- 成品图接管后**墨线必须退场**
- 切片边界用 `round(i*W/n)`，按精确区间摆放
